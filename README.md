# SubnetPal

Offline-first installable PWA for client-intake-driven IP planning (VLSM) on firewall builds. It turns a client intake into a network plan, a plain-language client report and a FortiOS CLI snippet. Vanilla HTML/CSS/JS, no framework, no build step, no dependencies.

## How to use

SubnetPal is one page. On a tablet or desktop the intake is a fixed left panel and the results scroll on the right, updating live as you type. On a phone the intake is a top section that collapses to a one-line summary ("Client: Acme · 5 networks") once you tap **Done**; tap the line to reopen it.

1. **Intake (left):** client name, site, staff count and expected growth (None 25% / Soon 50% / Big growth 100% buffer). **Import from contract** (top of the intake) fills the intake from pasted contract text, with a review step. **Load demo client** and **Clinic demo** add two made-up clients that show the whole flow. Tick **Guest wifi, Servers, DMZ, Voice / phones, Cameras, IoT, Printers or Card payments (POS)** to add that network; a count box appears only when the box is ticked. **+ Other** adds your own device pool (a name and a count, up to 10): each becomes its own network on the next free VLAN (90, 100, 110...), internet-only like IoT, reachable from Management, with a blank name becoming "Other n" and a blank count sized for 2. Staff LAN, Management and Transit/loopback are always planned. **More detail** holds existing IP ranges, the WAN/VPN note (client report only), the addressing style, an address block override and IPv6.
2. **Results (right)** are five tabs ("bookmarks") along the top, showing one section at a time: **Plan** (address map plus one card per network; tap a card for DHCP, static, broadcast, wildcard and host counts; tap any IP on a card to copy it), **Diagram** (the network diagram, SVG download or copy), **Policies** (firewall policies, below), **Remote** (IPsec remote access, below) and **Export** (the **Generate client documentation** button, plus FortiOS CLI, CSV and text, each with a Copy button).
3. The tab bar (Plan, Diagram, Export) stays pinned to the top of the results on desktop; there is no floating bar and nothing collapses. Plan is shown on load.
4. The client menu at the top of the intake switches clients. Duplicate, delete and sample clients are under it. Everything saves on the device automatically and works offline after the first load.
5. One warning banner appears at the top of the results only when something is wrong (an overlap with an existing range, the plan does not fit, or the addressing style had to fall back).

## Install on iPhone

1. Open the deployed `https://<you>.github.io/subnetpal/` URL **in Safari** (not Chrome).
2. Wait for the green **Offline ready** pill.
3. Tap Share, then **Add to Home Screen**, then Add. It opens full-screen and works in airplane mode.

## Run locally

```
node calc.test.js          # unit tests
node tools/serve.js 8080   # http://localhost:8080
node tools/make-icons.js   # regenerate icons (only if you change the design)
```

## Deploy to GitHub Pages

```powershell
git add .; git commit -m "Client intake flow"; git push
```

First-time setup (once): install GitHub CLI (`winget install GitHub.cli`, reopen PowerShell, `gh auth login`), then `gh repo create subnetpal --public --source=. --push` and `gh api -X POST "repos/{owner}/subnetpal/pages" -f "source[branch]=main" -f "source[path]=/"`. Live at `https://<your-github-username>.github.io/subnetpal/`. Netlify alternative: drag this folder onto https://app.netlify.com/drop.

Installed copies update on their next online open (cache-first with background refresh, so the new version shows on the launch after). When you ship changes, bump `CACHE` in `sw.js` (currently `subnetpal-v18`; new files go in `ASSETS`).

## Assumptions

**Planning**
- **Sizing:** needed = hosts + ceil(hosts x growth%) + network + broadcast + gateway, rounded up to a power of two; smallest block /30. Growth is not applied to /31 or /32.
- **Expansion:** None = 25%, Soon = 50%, Big growth = 100% (sets the growth buffer; it is used for sizing in packed style and for the "room to grow" figures in the client report).
- **Allocation:** largest first, each block aligned to its own size, placed in the lowest free spot that avoids existing ranges. Results display in address order.
- **/31 and /32:** role Transit with 2 or fewer hosts is a /31 (no gateway, no broadcast). Role Loopback (1 host) is a /32.
- **Existing ranges:** they are reserved wherever they fall inside the parent block. If the parent overlaps one (only possible when you override the parent), the plan still avoids it and shows a red warning. Existing ranges that overlap each other give a warning.
- **Parent auto-pick:** first free `10.x.0.0/16`, trying 10.20 upward then 10.2 to 10.19, then 10.0 and 10.1, then 172.16 to 172.31, then 192.168.0.0/16. If every option clashes, enter one manually. Typing an address block under More detail switches to manual; clearing it switches back to auto. Changing existing ranges on Intake re-picks an auto parent live.
- **Intake to networks:** Management, Staff LAN, Transit (/31) and Loopback (/32) are always planned. Servers, Guest, DMZ, Voice, Cameras and IoT are planned only when ticked. Servers is no longer always on.
  - Staff LAN = staff count. Every ticked network is sized from its count (minimum 2). Management = 10 hosts. DMZ and Servers get no DHCP range.
  - An unticked box is not planned, and any count typed earlier is ignored (the count box is hidden). A ticked box with no count is planned for 2 devices and a note says so (shown under "Unused space and notes").
  - The older wired and Wi-Fi counts are gone from the form. Clients saved earlier keep them and they are still added to the Staff LAN. Older clients keep Servers only if they had a servers count.
- **Addressing style (default one /24 per VLAN):** each network with a VLAN gets `<parent base>.<VLAN ID>.0/24`, so VLAN 20 in `10.20.0.0/16` is `10.20.20.0/24` with the gateway on `.1`. Transit (/31) and Loopback (/32) have no VLAN and share the third-octet-0 block (`10.20.0.0/31`, `10.20.0.2/32`). Every VLAN network is a /24 whatever its size, so the DHCP range simply fills the /24.
- **Fallback to packed VLSM:** if one /24 per VLAN is not possible, the plan uses the old packed VLSM and the warning banner says why. The reasons are: the parent is smaller than a /16, a VLAN ID is missing, above 255 or used twice, a network needs more than a /24 (over about 200 hosts with growth), or the /24 for a VLAN overlaps an existing range. You can also pick Packed yourself under More detail.
- **VLAN IDs:** Mgmt 10, Staff 20, Servers 30, Voice 40, Cameras 50, Printers 55, IoT 60, POS 65, Guest 70, DMZ 80; Transit and Loopback none. All editable. Generating again resets them.
- **Static and DHCP:** static reserve is the first N addresses after the gateway (default 10, clamped on small networks with a warning). DHCP follows the static reserve plus the offset. DHCP is offered on Staff LAN, Voice, Cameras, IoT and Guest, and not on Management, Servers, DMZ, Transit or Loopback.
- **No row editing:** the plan is always generated from the intake, live, so the Plan section has no editable rows (VLAN IDs, names and per-network options are not editable). Changing the intake replaces the plan. The only manual override is the address block under More detail. Clients saved earlier are regenerated from their intake when opened, so hand-edited rows from the previous version are not kept.

**Access rules (client report grid and FortiOS starter policies)**
- Staff: internet, Servers, DMZ. Servers: internet only. Voice: internet and Servers. Cameras: Servers only (no internet). IoT and Guest: internet only (Guest limited to DNS/HTTP/HTTPS). DMZ: internet only, explicitly blocked from internal networks. Guest is also explicitly blocked from internal networks.
- **Management restricted** is interpreted as: nothing else can reach Management; Management can reach internet and all other internal networks to administer them. Add an admin-workstation rule if admins connect from elsewhere.
- No inbound internet-to-DMZ policy is generated (it needs a VIP/port-forward decision). Transit and Loopback get no policies.

**Policy library (cards, `cards.js`)**
- **What a card is:** one rule idea with an id, name, source kinds, destination (kinds, the internet or all internal networks), service, action, a one-line `why` (the client need), `risk` (low/medium/high), `tier` (baseline/recommended/optional) and scenario `tags`. A card becomes one editable policy per matching pair of networks, and only when those networks exist in the plan (no POS network, no POS cards). Advice cards (remote VPN, site-to-site VPN, dual WAN, voice QoS, guest isolation, AP management, POS logging, cloud-only) never become policies; they show in the library with their guidance when their condition holds.
- **Scenarios covered:** staff LAN, guest, IoT, servers/DMZ, VoIP, printers, POS/PCI, management, Wi-Fi/AP, remote-access VPN, site-to-site VPN, dual WAN/failover. A test fails if a scenario has no card.
- **Tiers:** baseline is always on (everything the old starter policies contained is baseline, so existing plans export what they did before). Recommended is on by default. Optional is shown but off. The tier badge, risk badge and the `why` show on every policy that came from a card; policies you build yourself have none.
- **Switching cards:** the Policy library box in the Policies tab lists the cards that fit the plan. Before the first edit a tick only records the switch (`client.pol.toggles`) and the list keeps following the plan. After the first edit the list is frozen as before, and ticking a card adds its rules (or unticking removes only the rules that carry that card's id); your own policies are never touched. In a frozen list the checkbox shows whether the card's rules are present. **Reset to defaults** clears the frozen list and the switches.
- **Order:** narrow optional exceptions (POS to servers, DMZ to a database) first so the deny rules cannot shadow them, then explicit denies, then allows grouped by source network with the internet rule first.
- **New network kinds:** Printers (VLAN 55) and POS (VLAN 65), planned only when ticked, like the other optional networks. Printers: staff can print, printers cannot start connections inward and get no internet. POS: no access to anything internal, internet only on DNS, HTTPS and NTP to reach the payment provider (check your provider for other ports), staff are explicitly blocked from it.
- **Explicit denies added:** IoT, custom "Other" pools, printers and POS to internal networks, staff to POS, cameras to the internet, phones and cameras to Management. They change nothing in practice (the final deny already covers them) but make the intent visible and logged. Management stays the only network that may initiate to the others; "admin sources" are the Management network, with an optional "Staff LAN to Management" card (HTTPS, SSH, high risk, off by default) for admins who sit on the staff LAN.
- **Printing services:** staff-to-printers now uses a custom service `SP_PRINT` (TCP 9100, 631, 515), written by the FortiOS export as `config firewall service custom` only when a policy uses it (`CUSTOM_SERVICES` in `policy.js`). The service name is my own; the port list is standard (JetDirect, IPP, LPD). Verify on the lab VM when it is unparked.
- **Report access matrix** now follows the real policy list (optional cards you switched on, and your edits, show up), via `Access.matrixFromPolicies`. The default matrix, `Access.matrix`, is still used for the starter-rule tests.
- **Diagram, dual WAN:** the internet link reads "WAN1 + WAN2 (failover)" (client report: "Two internet connections (one is a backup)") when dual WAN is ticked. Site-to-site VPN is still not drawn.
- **Home-router clash wording:** when an existing range is itself a common home-router range, the banner says "is a range many home routers use" instead of "overlaps" itself.
- **Unverified (from memory, check on the lab VM):** the service names `MYSQL`, `MS-SQL`, `NTP`, `SIP`; SD-WAN zone wording in the dual-WAN advice; FortiAP being managed as local CAPWAP traffic with no policy; the "keep card-payment logs for about a year" advice.
- **Matrix:** the client report grid still comes from the access rules (`access.js`), which cover baseline and recommended cards. A test keeps the grid and the default policy list in step. Optional cards you switch on are not shown in the grid yet.

**Auto-suggest (`suggest.js`, pure functions)**
- **Intake answers:** under "About the site": Industry (office, clinic, school, retail; blank is treated as office), Servers (on-site or cloud only), Wi-Fi (FortiAP or third-party), Phones (hosted or on-site PBX), Dual WAN and Site-to-site VPN. They are stored on `client.intake` (`industry`, `serversWhere`, `wifi`, `voip`, `dualWan`, `siteVpn`; blank or false means not stated) and do not change the networks. **Printers** and **card payments** are the Printers and Card payments (POS) ticks in the network list, because they also create networks. Interface count and kinds come from the plan.
- **Office size** comes from the staff count (staff, or wired plus Wi-Fi when staff is blank): small up to 15, medium 16 to 75, large over 75. These cut-offs are my assumption.
- **How a card's state is decided:** baseline always on; recommended on by default; optional shown but off. The library gives each card a default tier, then the rules in `suggest.js` (`RULES`, a plain table, later rules win) can move it for the size, industry or answers, and each rule that fires adds its reason. Every card shows **Because:** the input that triggered it ("Guest wifi ticked") plus any rule reasons ("small site (8 staff, 5 networks): admin is usually one person"). You can still tick any recommended or optional card by hand.
- **What the rules do today:** the management lockdown is optional for a small office with fewer than 8 networks and recommended for medium, large, clinic, school or 8+ networks; hosted phones turn the phones-to-servers rule off, an on-site PBX keeps it; clinics keep the optional printers-to-internet card off with a reason; school and clinic sites add a reason to the cameras-blocked-from-internet rule (already on); retail with on-site servers is shown the optional POS-to-servers card with a warning that it widens card scope; third-party access points hint at the optional staff-to-management card. Dual WAN, site-to-site VPN, FortiAP/third-party Wi-Fi and cloud-only each add an advice card.
- **Notes under the library** flag answers that contradict the ticks (on-site servers but no Servers network, cloud-only but Servers ticked, phones but no Voice network, Wi-Fi but no Guest network, retail with no card payments, clinic or school with no guest network). They are prompts, nothing changes automatically.
- **Seeds only:** suggestions apply only while the list is untouched. The first edit freezes it exactly as before; changing an answer afterwards does not alter your list. **Reset to defaults** brings the suggestions back.
- **Client report and handover document:** a "Site profile" line appears under the requirements when any answer is set.

**Web filtering by FortiGuard category (`webcat.js`)**
- **Five groups:** Block always (malicious, phishing, spam URLs, proxy avoidance, and a botnets note), Block for most (adult, gambling, illegal, hacking, drugs, violence, weapons), Productivity (social networking, games, shopping, entertainment, dating), Bandwidth (streaming, peer-to-peer, software downloads) and Business-critical allow (file sharing and storage, web email, business, IT). Each group has an Allow / Warn / Block control on every policy.
- **ALL CATEGORY IDS ARE FROM MEMORY AND UNVERIFIED.** The seven already used before (26 Malicious Websites, 61 Phishing, 59 Proxy Avoidance, 37 Social Networking, 17 Gambling, 20 Games, 75 Streaming Media and Download) are unchanged; the rest were added from memory, and some may be wrong. The FortiOS export therefore prints one line listing every ID it uses next to the category it is meant to be, and a header that says the IDs are unverified. Check them on the lab VM before applying (the CLI help after `set category` should list the names). The Business group only matters if you set it to Warn or Block, because Allow writes nothing.
- **Botnets** is not a FortiGuard web category as far as I know, so it has no ID: the export prints a note to turn on botnet command-and-control blocking separately (unverified).
- **Actions:** Allow writes no entry (unlisted categories are allowed), Warn writes `set action warning` and Block writes `set action block`. A group set to Allow on every group adds no profile at all.
- **Presets per network type:** Staff (blocks Block always and Block for most, warns Productivity and Bandwidth), Guest (blocks the first two, warns Bandwidth), IoT and Servers (block everything except Business), Kids / BYOD (blocks the first three, warns Bandwidth). A custom "Other" pool gets Kids / BYOD when its name contains byod, kid, student, pupil, child, learner or school, otherwise IoT. DMZ uses the Servers preset. Voice, cameras, printers, POS and management get no profile. Changing one group on a policy makes it "Custom".
- **Industry presets:** school blocks the Productivity group (so social media) for staff and guests; clinic blocks the Bandwidth group (file sharing, peer-to-peer, streaming) for staff and guests; retail warns on guest Bandwidth. Office changes nothing. The Policies tab shows which one applies.
- **Where profiles attach:** only to Accept policies, and only to the cards that go to the internet (staff, guest, IoT, other pools, servers, DMZ). They sit on the policy as `webf` beside the older website/application lists (`web`, `app`), which still work and can be combined: both end up in one `SP_Web_n` profile and a category already listed is not repeated. Identical profiles are shared between policies, and the export says which policies use each one. Deny policies never get a profile, even if you edit one onto a deny.
- **On by default for new clients** ("Web filtering" tick under About the site). Saved clients from before this version are migrated to off so their exports do not change; tick it to turn it on. Turning it off on a client whose list is already frozen does not remove the profiles you have on it.
- **Known limit (unverified):** profiles use `certificate-inspection`, as before. With it, a category can be blocked from the site name, but a block or warning page may only display with deep inspection, so a Warn may behave like a block for HTTPS sites. Web filtering also needs a FortiGuard licence. Deep inspection is not generated.
- **Client report:** a "Web protection" section (numbered after Remote working) names the five groups in plain words and shows, per network, Blocked / Allowed after a warning / Allowed, plus the industry line. It never mentions category IDs or FortiOS. It is left out when no network has a profile.

**Demo clients**
- **Load demo client** (under the client menu) adds a made-up 25-person accountancy firm: 25 staff and 25 hosted-VoIP phones, guest Wi-Fi (10), a printer VLAN (3), two on-site servers, one IoT pool (6 devices), 5 remote staff, FortiAP Wi-Fi, card payments off, existing range `192.168.1.0/24` (so the home-router clash banner and report note show). **Clinic demo** adds a dental clinic: 12 staff, guest Wi-Fi in the waiting room, 2 isolated card terminals (POS), cameras, printers, an on-site phone system, one on-site server, third-party Wi-Fi, dual WAN, a site-to-site VPN and the clinic industry preset. Every load makes a new client, so nothing already saved is touched. The data is `DEMOS` in `intake.js`; the clients are invented.
- **They run end to end:** plan, diagram, suggested policies with their "because", web filter profiles, remote plan (accountancy only), the three exports and the client report. They are also the test cases for the suggestion engine (the two demos must give different rule sets: IoT rules only for the accountancy, POS rules and the on-site PBX server rule only for the clinic).
- **Client report, "The firewall rules, in plain language":** one row per rule in the list as it stands (so it follows your edits and switched-on cards): Allowed or Blocked, who can reach what in plain words (service names become "web browsing", "name lookups", "clock synchronisation"), the reason (the card's one-line why, which is written without technical terms), and the website checks on that rule. A rule you built yourself says "Added to suit your site." Sections after "Who can reach what" are numbered in order whichever apply (rules, room to grow, remote working, web protection, internet connection).

**Import from contract (`contract.js`)**
- **Files:** paste text, or choose a `.pdf`, `.docx` or `.txt` file. `.docx` is read by `docread.js` with no library (a minimal zip reader plus the browser's `DecompressionStream('deflate-raw')`, then the text of `word/document.xml`). `.pdf` is read by **PDF.js (pdfjs-dist 4.10.38, Apache-2.0) saved in `/vendor`** (`pdf.min.mjs`, `pdf.worker.min.mjs`, licence in `pdfjs-LICENSE.txt`), loaded only when a PDF is chosen and precached by `sw.js` so it works offline. **This is the one deliberate exception to the no-dependencies rule** (Steven approved, 24 Nov). Text only: nothing is rendered, uploaded or saved. Old `.doc` (before Word 2007) is refused with "save as .docx or PDF". Limits: 25 MB file, 200 PDF pages, scanned PDFs (no text layer) and password-protected PDFs give a clear message. The extracted text then goes through the same scanner and review screen.
- **Privacy:** the text is read in the browser and processed by pure functions. It is not saved to `localStorage`, not uploaded, not logged and not sent anywhere; only the values you apply are saved, as normal intake data. The text box and the review screen are cleared on Apply, Cancel and Clear. `extract()` returns only short snippets (under about 260 characters) of the sentences a value came from. The Intake box says so, and a test checks that `contract.js` contains no storage, network or DOM calls and that no contract wording ends up in the client record. The browser may keep what you typed in a form field until you clear it or close the page, so use Clear on a shared device.
- **How it works:** a rule per field (regular expressions over sentences and "Label: value" lines, in English): client name, site address, staff, guest Wi-Fi (and guest devices), IoT (and count), cameras (and count), servers (on-site or cloud-only, and count), remote staff (and count), industry, card payments (and terminals), internet type and number of lines (dual WAN), VoIP (phones, hosted or on-site, count), printers (and count) and site-to-site VPN. Numbers can be digits ("25", "1,200") or words ("twenty-five").
- **Never guesses:** a field with no clear statement is not returned and stays blank (listed under "Not found, left blank"). Where two things tie (for example school and shop for industry) nothing is returned. A bare "2 servers" gives a count but not whether they are on-site. "VPN" alone is not taken as remote staff. Numbers followed by or preceded by words such as remote, home, guest or visitor are not counted as the headcount. Dates, prices and contract terms are ignored.
- **Review screen:** each found field shows the value (editable), what the intake holds now, the source sentence with the matched words highlighted, and a confidence flag. **High**: an explicit label or a plain requirement ("Number of staff: 32", "shall include guest Wi-Fi"). **Check this** (medium): approximate or ranged figures (a range uses the higher figure), a plain mention, or a negative ("does not take card payments"). **Low**: two different figures or an opposite statement elsewhere (the others are listed), or wording such as optional, phase 2 or if required. Low rows start unticked; the rest start ticked. Nothing changes until you press **Apply selected to the intake**.
- **Applying:** counts, text and choices go first, then yes/no fields, so an explicit "No" beats a count that would have ticked the box. A count also ticks its network (guest devices tick Guest wifi). "Servers: on-site" ticks Servers; "cloud only" only sets the answer (the suggestion notes will tell you if Servers is still ticked). Internet type is added to the WAN note as a new "Internet: ..." line (once). The plan, suggestions and exports then follow as usual. The intake rules in this README (counts ignored when unticked, and so on) still apply.
- **Limits:** English only; one site per contract; it will miss unusual wording (that is the point of the review screen); it cannot tell which party an address belongs to unless it is labelled ("Site address:", "Premises:") or follows "installed at"; it reads at most about 400,000 characters.

**FortiOS output (generated, untested)**
- Includes interfaces, DHCP servers, one firewall address object per subnet (`SP_<name>`), an `SP_INTERNAL` address group and starter policies, with the note "Generated, untested. Verify against FortiOS 8.0 docs and the lab VM before applying. Starter policies are not production rules." at the top and bottom.
- One placeholder field (`PORT_CHANGE_ME` by default) is the parent port for VLAN interfaces (named `<Network>_V<ID>`, e.g. `Management_V10`) or the interface name for non-VLAN networks. The internet interface in policies is assumed to be `wan1`.
- `allowaccess` is least-privilege per network kind (`Access.adminAccess`): Management `https ping ssh`; staff, servers, phones, printers, DMZ, WAN `ping`; guest, IoT, cameras, card terminals and custom pools none (`unset allowaccess`). Roles map to `lan`, `dmz`, `wan` or `undefined`. Deny policies come first; allow policies use NAT toward the internet and `logtraffic all`.

**App**
- **Storage:** clients live in `localStorage` (key `subnetpal.v2`) on the device. Nothing is sent anywhere. Clearing Safari website data deletes them, so copy outputs you need. The earlier "named projects" data (key `subnetpal.v1`) is not migrated.
- **Validation:** hosts at least 1, VLAN 1-4094, names required and unique (case-insensitive), growth 0-500%, CIDRs strict (host bits set is an error). Duplicate VLAN IDs and non-RFC1918 parents are warnings. The IPv4 plan is the source of truth; IPv6 is added on top (see below).
- **Other pools:** stored in `intake.others` (`{name, count}`), names trimmed to 20 characters and made unique, so a pool never clashes with a built-in network. Their policy is fixed to the IoT rule (internet only, no access to other networks); change it by hand in FortiOS if a pool needs more.
- **CLI boxes:** the IPsec remote access CLI (Remote tab), the Policy CLI (Policies tab) and the FortiOS CLI (Export tab) each sit in a collapsible section with their copy button, closed by default. The CSV and Text exports are unchanged.
- **Tap-to-copy:** each IP on a network card (usable range start and end, port/gateway IP, netmask) is a button. A tap copies it and shows a short "Copied" toast (the address itself does not change or animate). It uses `navigator.clipboard` and falls back to a hidden textarea and `execCommand('copy')`, so it works offline and on plain http. If both are blocked it says so. The extra detail rows (DHCP, static, broadcast, IPv6) are not tappable.
- **Policies tab:** a policy is Source, Destination (a network, "All internal networks" or the Internet), Service, Action, NAT, Log, plus optional website and application profiles. Until you edit anything the list is the default access rules for the plan (the old starter policies) and follows the plan; the first edit freezes it as your own list (stored in `client.pol`), and **Reset to defaults** goes back. Policies are ordered, first match wins, and a fixed `SP_Final_deny` is always last. A policy naming a network that is no longer in the plan stays in the list, is flagged, and is skipped in the CLI with a comment. The old fixed starter policies are gone from the FortiOS export: it now exports this list (IPv6 mirrors it without profiles). **Copy policy CLI** copies just the address objects, profiles and policies; the full snippet is under Export.
- **Tagline parser (offline, rule-based, `policy.js`):** clauses are split on full stops, semicolons, commas and new lines. Network names are matched against the plan (case-insensitive, plural/singular, plus aliases such as guests/visitors, phones/voice, cctv, "the internet"). The first network named is always the source and the second the destination. Templates: "X internet only" / "...but nothing else" (accept to the internet plus a deny to internal, and it replaces X's other policies), "X can't / cannot / must not reach Y", "X blocked from Y", "X can reach Y [on https, ssh, web, dns, rdp, smb, email, ping...]". A service word it does not know, a single network name, or no known phrase makes the clause "not understood": it is listed with the reason, nothing is guessed, and you build the policy with the dropdowns. Parsed denies are put at the top, then accepts, replacing any existing policy with the same source and destination. "X and Y can ..." (two sources in one clause) is not supported.
- **Website and application profiles:** websites are a block-list or an allow-list (allow-list adds a final `*` block entry) built as a URL filter table plus web filter profile; applications are a category block-list or allow-list (allow-list ends with a catch-all block entry). They attach to Accept policies only, with `utm-status enable` and `certificate-inspection`. **FortiGuard web category IDs and application category IDs are from memory and unverified**, and the profile/table names (`SP_Web_n`, `SP_App_n`, URL filter table ids 101+) may clash with existing ones on a real unit. All policy output carries the "Generated, untested. Verify profile and setting names..." note.
